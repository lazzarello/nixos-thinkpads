# NixOS configuration — ThinkPad P1 (`20MDCTO1WW`)

Declarative configuration for a ThinkPad P1 running NixOS 26.05 with Niri.

## Why rebuild commands need `--flake`

Enabling the `nix-command` and `flakes` experimental features allows flake
commands; it does not automatically make `nixos-rebuild` use this repository.
Without `--flake`, the installed rebuild tool looks for `/etc/nixos/flake.nix`.
That file is absent here: `/etc/nixos` contains symlinks to selected modules,
not to the flake. Running the command from `~/nixos` does not change that
default lookup.

The command therefore falls back to the legacy `<nixpkgs/nixos>` entry point,
which looks up `configuration.nix` through `NIXOS_CONFIG` or the `nixos-config`
Nix search-path entry. The reported error:

```text
error: file 'nixos-config' was not found in the Nix search path
```

means that legacy lookup failed. It is not a failure to evaluate `flake.nix`;
the flake was never selected. Adding a legacy `NIX_PATH` entry alone would not
make the command evaluate the flake or provide its Voxtype and unstable
package inputs.

In `sudo nixos-rebuild switch --flake ~/nixos#nixos`:

- `~/nixos` selects the directory containing `flake.nix` and `flake.lock`.
- `#nixos` selects `nixosConfigurations.nixos`, the output declared in
  `flake.nix`. This is an output name, not necessarily the machine's hostname.
- Omitting `#nixos` makes the rebuild tool use the hostname, currently
  `phillip`. This flake does not export `nixosConfigurations.phillip`, so
  `--flake ~/nixos` alone would select a nonexistent configuration.

The absolute path is not required: from this repository, `--flake .#nixos`
works too. The same selector applies to `build`, `switch`, and `boot`.

To make bare `nixos-rebuild` commands work, you could add an
`/etc/nixos/flake.nix` symlink pointing at this repository's flake and export a
configuration matching the hostname. Those are optional configuration changes;
the commands below deliberately keep the flake and output explicit.

## Layout

| File | Owns |
|---|---|
| `configuration.nix` | Base system: bootloader, networking, users, locale, sudo |
| `hardware-configuration.nix` | Generated by the installer. Filesystems, LUKS, microcode |
| `desktop.nix` | Compositor, shell, greeter, audio, cursor theme |
| `discord.nix` | Official Discord bootstrap and compatibility libraries; upstream client updates |
| `scripts/` | Shell scripts and script templates loaded by the Nix modules |

The working tree lives in `~/nixos`. The files in `/etc/nixos` are symlinks
into it, so edits and `git` never need `sudo`. `/etc/nixos` itself is not
NixOS-managed, so those symlinks survive activation.

```sh
ls -l /etc/nixos      # -> /home/lee/nixos/*.nix
```

## Usage

```sh
cd ~/nixos
$EDITOR desktop.nix

sudo nixos-rebuild build --flake .#nixos   # build only, produces ./result, no activation
sudo nixos-rebuild switch --flake .#nixos  # activate now, and set as boot default
sudo nixos-rebuild boot --flake .#nixos    # activate on next boot only
```

From another directory, use `--flake ~/nixos#nixos` instead. New files referenced
by the configuration must be added with `git add` before rebuilding: Git-backed
flakes exclude untracked files. Existing tracked edits do not need a commit
before they can be built.

Commit after a `switch` succeeds, so `git log` tracks known-good states.
If a rebuild breaks the desktop, pick the previous generation in the
systemd-boot menu, then `git revert`.

## Discord

Launch **Discord** from the application menu or run `discord`. The official
Linux bootstrap downloads the current stable client on first launch. Discord
then handles its own updates directly from upstream; updating `flake.lock` or
rebuilding NixOS is not needed for client releases.

`discord.nix` installs a pinned, unmodified bootstrap and runs it in a
`buildFHSEnv` environment that supplies conventional Linux library paths.
The downloaded client, updater, and settings live in `~/.config/discord`
(or `$XDG_CONFIG_HOME/discord`). The Nix store holds only the bootstrap and
compatibility environment, so client updates can write to the user directory.
NixOS rollbacks restore the wrapper, while the client stays at its upstream
version. Do not install the separate nixpkgs `discord` package alongside this
wrapper: both provide the same command and use the same settings directory.

## Verified behavior

Tested 2026-09-21 on this hardware. All checks passed.

| # | Check | Result |
|---|---|---|
| 1 | Niri renders on Intel; NVIDIA runtime-suspends | PASS |
| 2 | HDMI hot-plug, both screens usable | PASS |
| 3 | Disconnect leaves windows reachable on the panel | PASS |
| 4 | NVIDIA returns to idle suspend after unplug | PASS, ~7 s |
| 5 | Suspend/resume, HDMI connected and disconnected | PASS |
| 6 | Audio follows output changes | PASS (recording/brightness/battery still open) |

Details worth keeping:

- **Hot-plug.** The LG 4K is detected by name and gets its preferred
  3840x2160@60 with no manual config. Niri places it at logical x=1707,
  directly right of eDP-1's 1706 px logical width. Each output keeps its own
  workspace set.
- **NVIDIA power.** Unplug to `suspended` takes about 7 s, consistent with
  `power/autosuspend_delay_ms=5000`. Across a session with four hot-plug
  cycles the card was suspended ~93% of the time. The audio function
  `0000:01:00.1` suspends too.
- **Suspend is real S3**, not a reboot: `PM: suspend entry (deep)` →
  `ACPI: PM: Waking up from system sleep state S3`. The niri process keeps the
  same PID across cycles, and both outputs return to identical geometry.
- **Nouveau survived all of it** with zero driver errors, including waking the
  Quadro to restore a 4K external mode. The proprietary `legacy_580` branch is
  therefore **not needed**. Do not switch drivers without a reason.
- **Audio crosses a GPU boundary.** HDMI audio is on the NVIDIA card
  (`card 0`, `GP107GL`); the analog headphone jack is on the Intel PCH
  (`card 1`). WirePlumber switches between them automatically on plug, and
  each sink keeps an independent volume.

Two log lines look alarming on resume but are benign:

```
mei_hdcp ...: bound 0000:00:02.0 (ops i915_hdcp_ops [i915])   # HDCP rebind
usb 1-8: reset high-speed USB device ... using xhci_hcd        # USB re-enumeration
```

### Reproducing the checks

`niri msg` needs the socket, which an SSH session does not inherit:

```sh
export NIRI_SOCKET=$(ls -t /run/user/1000/niri.wayland-*.sock | head -1)
niri msg outputs
```

```sh
# connector states and GPU power
for c in /sys/class/drm/card*-*/status; do echo "$c $(cat $c)"; done
cat /sys/bus/pci/devices/0000:01:00.0/power/runtime_status

# suspend cycles, and driver errors across them
journalctl -k -b | grep -E 'PM: suspend (entry|exit)|sleep state S3'
journalctl -k -b | grep -iE 'nouveau.*(fail|error|timeout)|i915.*(fail|error|hang)'

# audio sinks
XDG_RUNTIME_DIR=/run/user/1000 wpctl status
```

## Hardware notes

Dual GPU. Niri renders on the Intel iGPU and leaves the NVIDIA Quadro
runtime-suspended until something needs it:

| Device | PCI | Driver | Role |
|---|---|---|---|
| Intel UHD P630 | `0000:00:02.0` | `i915` | Primary renderer, internal eDP panel |
| NVIDIA Quadro P2000 | `0000:01:00.0` | `nouveau` | Drives HDMI/DP, suspends when idle |

Verify the render node after changes — do not assume it from `boot_vga`:

```sh
journalctl --user -b -t niri | grep 'render node'
# want: using as the render node: "/dev/dri/renderD128"   (= Intel)
ls -l /dev/dri/by-path/
cat /sys/bus/pci/devices/0000:01:00.0/power/runtime_status
```

## Idle, lock and suspend policy

Ownership is split, and it matters:

| Behavior | Owner | Setting |
|---|---|---|
| Lid close → suspend | logind | `HandleLidSwitch=suspend` (default, works) |
| System idle action | logind | `IdleAction=ignore` — deliberately unused |
| Idle → blank / lock / suspend | **DMS** `IdleService` | per-power-source timeouts |
| Lock before suspend | **DMS** | `lockBeforeSuspend` |

DMS owns idle rather than logind because it uses the Wayland idle-notify
protocol, so it sees real input activity and respects inhibitors — fullscreen
video will not blank the screen. logind's `IdleAction` cannot do that. Do not
configure both.

Current values (seconds; `0` means never):

| | AC | Battery |
|---|---|---|
| Monitor off | 900 (15 m) | 300 (5 m) |
| Lock | 1200 (20 m) | 600 (10 m) |
| Suspend | 0 (never) | 1800 (30 m) |

Keep `lock >= monitor-off` and `suspend > lock`, so the screen blanks before it
locks and locks before it sleeps.

**These live in `~/.config/DankMaterialShell/settings.json`, which is mutable
user state — not NixOS-managed and not in this repo.** Generations will not roll
it back. DMS rewrites the file at runtime, so change it through the DMS settings
UI, not by hand. Back it up if you care:

```sh
cp ~/.config/DankMaterialShell/settings.json ~/nixos/dms-settings.json.bak
```

## Gotchas found the hard way

**Hand edits to generated files in `/etc` are discarded on activation.**
`visudo` edits to `/etc/sudoers` worked until the next `nixos-rebuild`, then
vanished. Most of `/etc` is a symlink into the store and fails loudly when
edited, but files needing restrictive modes (like `sudoers`, mode `0440`) are
*copies*, so edits succeed and are silently reverted later. Check
`ls -l /etc/static/<file>` to see whether NixOS owns something.

**Cursor themes needed three separate fixes.** An invisible mouse pointer at
the login screen, but a working one in Niri, turned out to be three causes:

1. No xcursor theme was installed at all — only `hicolor` and `locolor`,
   neither of which contains a `cursors/` directory.
2. Nothing set `XCURSOR_THEME`, so clients requested the theme literally
   named `default`, which did not exist. Niri has a built-in fallback bitmap
   and stayed usable; Weston has none and drew nothing.
3. `services.displayManager.sddm.settings.Theme.CursorTheme` is inert under
   `DisplayServer=wayland`. sddm 0.21 applies it only on the X11 path — the
   package contains no reference to `XCURSOR`.

See the comments in `desktop.nix` for the details.

**A shell can hide whole features when a service it reads from is missing.**
The "Power source" AC/Battery selector in DMS's Power & Sleep settings simply
was not rendered, making the battery-side idle timeouts unreachable. The
battery was fine — `BAT0` read 98% in sysfs the whole time. But DMS reads
batteries through **UPower**, not sysfs:

```qml
// BatteryService.qml
readonly property var batteries: UPower.devices.values.filter(dev => dev.isLaptopBattery)
readonly property bool batteryAvailable: batteries.length > 0
```

`services.upower.enable` was `false`, so `batteryAvailable` was false and every
battery-conditional control was hidden. The `programs.dms-shell` module enables
`power-profiles-daemon` but not `upower`.

General lesson, and it recurred three times in this setup: when a setting seems
not to apply, verify *which API the consumer actually reads* before assuming the
value is wrong. Checking sysfs proved nothing about what DMS could see, just as
setting `CursorTheme` proved nothing about what Weston read.

**`power-profiles-daemon` is enabled by the DMS module**, not by this config. Do
not add TLP without deciding which daemon owns power management; they conflict.
